# Backup-as-code

A Terraform configuration that describes every inbound, every client, and every panel setting *is* a backup — one that lives in git, is reviewable, and can be replayed against any 3x-ui host.

This guide shows the minimum setup to keep your panel state in git and how to restore from it after a failure.

## What you get

- **Point-in-time history** — every change is a commit. `git log` is your audit trail.
- **One-command restore** — point Terraform at a fresh panel and `apply`.
- **Review before merge** — pull requests catch accidental client deletions before they hit prod.
- **Drift detection** — `terraform plan` flags any change made through the UI behind your back.

## Layout

```text
panel-backup/
  main.tf            # provider + locals
  inbounds.tf        # all inbounds
  clients.tf         # all clients
  panel.tf           # general/security/telegram/subscription settings
  xray.tf            # routing, DNS, outbounds
  terraform.tfvars   # endpoint + credentials (gitignored)
```

## Provider configuration

```hcl
terraform {
  required_providers {
    threexui = {
      source = "batonogov/threexui"
    }
  }
  backend "s3" {
    bucket         = "panel-state"
    key            = "production/terraform.tfstate"
    region         = "eu-central-1"
    encrypt        = true
    dynamodb_table = "tf-locks"
  }
}

provider "threexui" {
  endpoint = var.endpoint
  username = var.username
  password = var.password
}
```

## Importing what you already have

If the panel is already populated, import it once instead of recreating it:

```bash
# inbounds (look up IDs in the panel or via the API)
terraform import threexui_inbound.vless 5
terraform import threexui_inbound.trojan 6

# clients use composite IDs: <inbound_id>:<client_uuid>
terraform import 'threexui_inbound_client.alice' '5:d4f1a2b3-c4d5-6e7f-8a9b-0c1d2e3f4a5b'

# panel settings are singletons
terraform import threexui_panel_general.this settings
terraform import threexui_panel_telegram.this settings
```

After import, run `terraform plan` and copy non-default attributes into your `.tf` files until the plan is clean.

## Daily flow

1. Someone proposes a change as a PR (`feat: add three new clients for team-x`).
2. CI runs `terraform plan` against staging and posts the diff as a PR comment.
3. A reviewer approves; merging triggers `terraform apply`.
4. The panel and the git history stay in lock-step.

## Restoring after a panel loss

```bash
# 1. Spin up a fresh 3x-ui on the new host
docker compose up -d

# 2. Update var.endpoint to point at the new host
echo 'endpoint = "https://new-host:2053"' > terraform.tfvars

# 3. Apply — the provider re-creates everything from your repo
terraform apply
```

Reality keys, WireGuard secrets, and short IDs that were auto-generated by the previous panel are stored in your Terraform state. They are re-applied verbatim, so existing client configs (QR codes, links you shipped to users) keep working.

## What to watch out for

- **State is the source of secrets.** Encrypt your remote backend. See [SECURITY.md](../../SECURITY.md).
- **`threexui_panel_user` is write-only.** Changing the admin password through Terraform is supported, but the provider has no API to read the current password back, so the resource trusts state.
- **Subscription resource double-applies.** Known 3x-ui quirk; the provider works around it transparently.
